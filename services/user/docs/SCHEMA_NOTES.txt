СОПОСТАВЛЕНИЕ ФОТО, КОНТРАКТА BFF И РЕАЛИЗАЦИИ

На фото image(20261018-155840).png показана топология сервисов. Слева таблицы почти
полностью обрезаны; прочитать их схему по этому фото нельзя.
На image(20261018-155844).png читаются основные поля нашей таблицы User:
login, role (ADMIN, COMMON), hashPswd, deletedAt, isDeleted, birthDate, fullName,
avatarUrl. Нижняя граница блока у края кадра: утверждать, что ниже нет других полей,
по снимку нельзя. У Tokens читаются user_id, tokenHash, expireAt, isValid; точное
написание временного поля от руки неоднозначно. Слово UUID написано отдельно.

Соседние блоки Ride/Payments, Documents и Moderation местами читаются хуже;
например, написание имени rides и полей start/finish, а также типы, ключи и nullability
по этим фото достоверно не определяются. Они не выдаются за готовую SQL-схему.
Эти таблицы не создаются в БД User: у команд отдельные базы по схеме топологии.

Итоговые решения для нашей БД:
User -> users; UUID -> id UUID PK, UUID создаётся приложением.
login -> login VARCHAR(64), уникальный, нормализованный в нижний регистр.
hashPswd -> password_hash VARCHAR(60), BCrypt, никогда не возвращается в API.
role ADMIN/COMMON -> role ADMIN/USER, чтобы совпали BFF и ожидания Moderation.
fullName -> full_name VARCHAR(200), birthDate -> birth_date DATE,
avatarUrl -> avatar_url VARCHAR(2048), isDeleted -> is_deleted,
deletedAt -> deleted_at TIMESTAMPTZ. JSON остаётся camelCase, deleted вместо isDeleted.
created_at и updated_at добавлены для жизненного цикла записей.
Удаление согласовано CHECK: is_deleted истинно тогда и только тогда, когда есть deleted_at.
Публичной ручки удаления/изменения профиля нет, потому что её нет в запрошенном контракте.

Tokens -> tokens; id UUID соответствует jti JWT, user_id -> users.id,
tokenHash -> token_hash SHA-256, expireAt -> expire_at, isValid -> is_valid,
created_at — время выдачи. Сырой JWT в БД не хранится. Таблица сохранена с доски,
хотя для одной проверки криптографической подписи JWT она сама по себе не обязательна.
Она нужна для отзыва и проверки активности входа в User/BFF.

Blocked отсутствует в users: его источник Moderation.user_states.
Роль хранится у нас, как на фото User и в текущем задании. Moderation читает её из
подписанного JWT, отдельная копия роли в её БД не нужна.

В текстовой спецификации часть интерфейсов помечена [предложение]. В проекте эти
предложения реализованы и описаны в API.txt, но они всё ещё требуют принятия командой
Moderation: RS256/issuer/public.pem, путь status и его ответ, ban/unban, справочник,
права self-or-admin, 200 blocked=false при отсутствии записи. Исходников Moderation
среди вложений нет, поэтому подтвердить её фактический контракт невозможно.

Приложенный BFF уже исправляет обработку 5xx проверки blocked на 503, убрал role из
AuthRequest регистрации и при login отправляет только login/password. Текст спецификации
в этих местах отстаёт от кода. Наш код совместим с обоими вариантами: присланная роль
не влияет на регистрацию, дополнительные поля login игнорируются.
В BFF нет прокси GET /api/users, GET /api/users/{id}, ban/unban и админских списков;
для предложенного прямого вызова из панели они не нужны. Если требовать все вызовы
только через BFF, его команда должна добавить эти прокси и админский редирект.

Актуализация входа: основной login.jsp принадлежит BFF. Команда BFF сама добавляет
редирект по user.role === ADMIN. User содержит только REST API, без страниц входа,
фронтенда и отдельного admin-login API. LoginRequest с
@JsonIgnoreProperties(ignoreUnknown = true) принимает дополнительные null-поля BFF.
В итоговой схеме ровно users и tokens, физическое имя времени истечения — expire_at.
Для установленной предыдущей версии предоставлен отдельный скрипт переименования 002.
