1) Да, JWT содержит userId — UUID пользователя строкой, и role — строго USER или ADMIN. Подпись RS256, issuer по умолчанию scooter-user-service, срок 3600 секунд. Передадим вам public.pem для проверки подписи. Публичная регистрация всегда создаёт USER, присланная роль игнорируется. ADMIN назначается отдельно оператором.

2) GET /api/users реализован и возвращает массив [{"id":"UUID","login":"ivan","fullName":"Иван Петров"}]. Доступ только с Authorization: Bearer <JWT> роли ADMIN: без токена — 401, с USER — 403. Есть GET /api/users/{id} для ADMIN или самого пользователя, с 404 для отсутствующего активного пользователя.

3) Основной вариант — единый вход через уже готовую login.jsp команды BFF. Если у вашей панели нет токена, перенаправляйте администратора туда. Адрес — <базовый URL BFF>/login.jsp с учётом context path; точный адрес нужно взять у команды BFF. Например, при BFF на localhost:8080 с ROOT-развёртыванием это http://localhost:8080/login.jsp, при контексте /scooter-bff — http://localhost:8080/scooter-bff/login.jsp. Сам User Service остаётся REST API и возвращает accessToken, expiresInSeconds и user.role.

Задача команде BFF: в js/login.js заменить текущую строку await apiRequest('/api/auth/login', jsonOptions('POST', values)); на эти 4 строки. Существующую строку перехода в main.jsp ниже оставить для USER. В их текущем api.js apiRequest возвращает Response, поэтому сначала нужен response.json(). Адрес панели в примере заменить фактическим адресом Moderation:

const { user, accessToken } = await (await apiRequest('/api/auth/login', jsonOptions('POST', values))).json();
if (user.role === 'ADMIN') {
  location.replace('http://localhost:8082/admin/users.html#accessToken=' + encodeURIComponent(accessToken)); return;
}

Это задача команды BFF: исходники и архив BFF мы не меняли. User Service предоставляет только REST API и не содержит страниц входа. Проверку прав админских API выполняют серверы. На вашей стороне сразу заберите токен из фрагмента в sessionStorage и очистите URL через history.replaceState.

4) CORS-фильтр есть. Ваш origin задаётся в CORS_ALLOWED_ORIGINS, для локального стенда по умолчанию http://localhost:8082. Возвращаем Access-Control-Allow-Origin для разрешённого origin, разрешаем Authorization, Content-Type, Accept и методы GET, POST, OPTIONS. Preflight OPTIONS получает 204 до проверки JWT; CORS-заголовки сохраняются и на ошибках. Список пользователей запрашивайте с Authorization: Bearer <JWT>, без cookies. На общем стенде localhost заменяется фактическими адресами сервисов.

По интеграции блокировок: данные храните вы, у нас blocked в БД нет. Для профиля и GET /api/users/{id}/blocked вызываем ваш GET /api/moderation/users/{userId}/status с исходным Authorization: Bearer <JWT>. Ожидаем 200 {"userId":"UUID","blocked":true/false}; отсутствие блокировки — 200 с blocked=false, а не 404. Status доступен самому пользователю и ADMIN. При недоступности или 5xx вашего сервиса отдаём 503. Прокси POST /api/users/{id}/ban, POST /api/users/{id}/unban и GET /api/users/blocked реализованы и доступны только ADMIN.
