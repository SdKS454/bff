# Проверка перед сдачей

Версия для сдачи: 27 октября 2026. Проверять текущий main или тег
`submission-2026-10-27`, а не прежние архивы коллег/handoff.

## 1. Запуск

Нужны Git/ZIP проекта, запущенный Docker Desktop с Linux-контейнерами и браузер.
Для ручной проверки Java, Maven, Node.js и отдельный PostgreSQL устанавливать не нужно.
Порты 8080–8085 и 54320 должны быть свободны.

```bash
docker compose up --build -d
docker compose ps -a
```

Ожидается: postgres и шесть приложений — healthy; keys и migrate — Exited (0).
Это успешные одноразовые задачи. При первой сборке нужен интернет. Если запуск
неуспешен: `docker compose logs --tail=100 postgres migrate user bff`.
Сайт: **http://localhost:8080/**. Все публичные приложения работают в контексте `/`.

Обновление существующего стенда: та же команда up --build. Миграции применяются
автоматически и не стирают пользователей/поездки. Изменённый задним числом файл
уже применённой миграции вызывает ошибку, вместо незаметного изменения схемы.
Не используйте `down -v` для обычного обновления: эта команда удаляет данные/ключи.

## 2. Аккаунты для демонстрации

Можно создать USER и будущего ADMIN обычной регистрацией, затем назначить роль:

```bash
docker compose exec user java -cp '/usr/local/tomcat/webapps/ROOT/WEB-INF/classes:/usr/local/tomcat/webapps/ROOT/WEB-INF/lib/*' ru.scooter.user.cli.PromoteAdmin your.admin.login
```

В PowerShell classpath можно заключить в двойные кавычки. После повышения роли
нужно войти заново: старый JWT отзывается.

При наличии Node.js есть необязательная автоматическая подготовка:

```bash
node scripts/prepare-demo.cjs
```

Будут подготовлены `demo.user` / `demo.admin`, пароль `Demo-password-2026!`.
Скрипт не удаляет данные и не сбрасывает существующий другой пароль. При конфликте
логинов выберите DEMO_USER_LOGIN / DEMO_ADMIN_LOGIN / DEMO_PASSWORD. Демонстрационные
аккаунты создаются только по явному запуску скрипта, не при каждом старте приложения.
Для USER и ADMIN используйте **разные профили браузера / инкогнито**: вкладки одного
профиля разделяют cookie BFF и не подходят для двух независимых сессий.

## 3. Обязательный ручной прогон

Отмечайте результат каждого пункта. Проверка занимает примерно 15–20 минут.

| № | Действие | Ожидаемый результат |
| --- | --- | --- |
| 1 | Открыть сайт без входа | Оформление загружается, нет вымышленного каталога вместо API; предложен вход |
| 2 | Зарегистрировать нового пользователя: латинский логин, пароль ≥8 символов, ФИО, дата рождения | Создан USER, выполнен вход, профиль содержит введённые данные |
| 3 | Повторить регистрацию того же логина, включая другой регистр букв | Понятная ошибка занятого логина; второй пользователь не создан |
| 4 | Проверить пустые ФИО/дату, пароль короче 8, будущую дату рождения | Запрос отклонён, ошибочные данные не сохранены |
| 5 | Выйти, попробовать неверный пароль, затем верный | Неверный вход отклонён; верный восстанавливает кабинет |
| 6 | Нажать F5 после входа | Сессия сохраняется; устаревшая форма регистрации/входа не открывается снова из старого auth URL |
| 7 | Открыть каталог/карточку | Самокаты с реальными номерами, зарядом и статусами из Scooter; занятый/заряжающийся нельзя взять |
| 8 | Найти по координатам X=10, Y=15 | Только READY, по возрастанию расстояния в единицах **учебной сетки**; GPS-кнопки нет |
| 9 | Добавить самокат в избранное и обновить страницу | Избранное сохраняется на этом устройстве отдельно для пользователя |
| 10 | Начать поездку свободным самокатом | Перед стартом виден тариф 50 ₽ + 8 ₽/начатая минута и учебный режим; после старта ACTIVE, Scooter IN_RIDE |
| 11 | Попробовать вторую активную поездку этим пользователем / тот же самокат другим пользователем | Отказ; нет двойного резервирования и второй активной поездки |
| 12 | В «Моих поездках» обновить позицию: X=12.125, Y=16.75 | Показана последняя позиция; Scooter хранит те же дробные значения; стоимость от этого не меняется |
| 13 | Завершить поездку: X=20.5, Y=25.75 | FINISHED, Scooter снова READY в конечной позиции, рассчитана сумма |
| 14 | Сверить сумму с длительностью | 50 + 8 × max(1, ceil(durationSeconds/60)): до 60 секунд — 58 ₽, 61–120 — 66 ₽; тариф берётся из снимка начатой поездки |
| 15 | Подтвердить учебную оплату | PAID, есть paidAt; явно указано отсутствие банковского списания |
| 16 | Скачать чек | Открывается настоящий PDF с кириллицей, номером поездки/самоката, суммой и учебной пометкой |
| 17 | Сформировать PDF истории за даты поездки (период по UTC) | PDF содержит собственные поездки выбранного периода |
| 18 | Открыть «Документы» | Есть история генераций, тип/дата/статус; можно скачать сформированный документ повторно |
| 19 | После PDF истории совершить ещё одну поездку и скачать старый документ по ID | Старый PDF сохраняет исходное содержимое; новый PDF истории включает новую поездку |
| 20 | Удалить документ из истории, сначала отменив подтверждение | При отмене запись остаётся; после подтверждения исчезает; повторное скачивание удалённого ID даёт 404 |
| 21 | Под ADMIN войти через /login.jsp | Переход на http://localhost:8082/admin/users.html; токен убран из адреса, таблица пользователей загружена |
| 22 | В админке заблокировать обычного пользователя | Профиль USER после обновления показывает бан; старт запрещён; доступно PDF-уведомление |
| 23 | Если USER уже ехал, завершить и оплатить поездку после бана | Завершение и учебная оплата разрешены, новый старт — нет |
| 24 | Снять бан | Новый старт разрешён; новая генерация уведомления о текущем бане — 409; ранее сформированное уведомление скачивается из снимка |
| 25 | Закрыть «Документы» сразу после запроса обновления | Поздний ответ не открывает закрытое окно и не очищает введённые даты |
| 26 | Выйти из кабинета/админки и обновить страницу | Приватные данные не отображаются; отозванный JWT больше не принимается сервисами |
| 27 | Выполнить docker compose down, затем docker compose up -d | Пользователи, история, документы и ключи сохранены. BFF может потребовать новый вход после остановки своей сессии |

Новая генерация и скачивание по ID — разные действия: повторный download не
создаёт ещё одну запись истории. PDF-файлы не хранятся; сохраняется снимок исходных
данных, по которому повторно формируется то же содержимое. Для старых записей
версии 26 октября без снимка используется восстановление из доступных источников;
утраченные исторические данные не выдумываются. Для проверки п.19/24 создайте
документы после обновления до сдаваемой версии.

Удаление мягкое: запись остаётся в БД с is_deleted=true, но недоступна в API/списке.
Незавершённая генерация, зависшая более двух минут, при чтении истории получает
FAILED; её можно повторить отдельной генерацией. Бессрочный PAYMENT_DEBT снимает
администратор вручную: учебная оплата произвольной поездки не снимает чужой бан.

## 4. Автоматическая проверка для разработчика

Нужны Java 17+, Maven 3.9+, Node.js 22+, Chromium/Playwright, pdftotext и Docker.
На Linux pdftotext входит в poppler-utils. На Windows установите Poppler и добавьте
pdftotext в PATH. Для PDF unit-тестов задайте PDF_FONT_PATH к TTF с кириллицей.

```bash
mvn clean verify dependency:build-classpath -Dmdep.outputFile=target/test-classpath.txt
npm ci
npx playwright install chromium
npm test
npm run test:e2e
```

Для тестов микросервисов: `mvn -f services/ИМЯ/pom.xml verify`.
Для JDBC-тестов User нужны TEST_DB_URL/TEST_DB_USER/TEST_DB_PASSWORD;
они создают отдельную тестовую схему, а не стирают public.

Для полной проверки с намеренными остановками сначала остановите рабочий
стенд обычным down (**без -v**), поскольку порты общие:

```bash
docker compose down
docker compose -p kicksharing-full-check up --build -d
node scripts/check-full-stack.cjs
node scripts/check-submission.cjs
node scripts/check-stack-recovery.cjs
docker compose -p kicksharing-full-check down
docker compose up -d
```

Рабочий и тестовый проекты используют разные volumes. Тесты создают свои
аккаунты/поездки и намеренно перезапускают сервисы только в проекте
kicksharing-full-check*. Успех — PASS в конце каждого сценария, без исключений.
Сохраняйте логи неудачного шага, а не только последний экран браузера.

## 5. Что показать преподавателю

1. Главную страницу, вход USER, поездку, стоимость и учебный чек.
2. Отдельную сессию ADMIN: бан/разбан и запрет старта.
3. Историю документов, повторный PDF из снимка и soft delete.
4. Независимые контейнеры, пять БД, таблицы rides/rates/documents/scooter_reservations.
5. [Архитектуру и ответы для защиты](DEFENSE.md), [REST-контракт](API_CONTRACTS.md),
   этот чек-лист и отчёт фактического прогона [SUBMISSION_REPORT.md](SUBMISSION_REPORT.md).

GitHub Actions выполняет проверку при push в main и для pull request.
Его результаты находятся во вкладке Actions; наличие workflow не заменяет
проверку фактического статуса конкретного запуска.
